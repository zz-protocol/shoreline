## 一、[P0] 非 UTF-8 标题导致 http 任务整体失败（35 次失败，36%）

已单独出详细报告：`BUG-非UTF8标题导致HTTP扫描全任务失败.md`

- 位置 `httpprobe.go:157-159`（标题未解码）+ `592`（单条失败废整任务）
- 复现：`http://gdinfo.95516.com/`（`charset=gb18030`，title 字节 `d3 c3 bb a7 b5 c7 c2 bc`）
- **附加影响（本次新发现）**：任务因该错误反复重试，每轮重试都会重新探测并改状态 → **放大事件噪声**。例：`360.cn` 的 http 任务重试 4 次，24h 内产出 **949 条 recovered 事件**（占全站 recovered 的 20%）。

## 二、[P1] CDN CNAME 轮换 → changed 事件风暴

**24h 统计：changed 2,889 条 / 涉及 1,648 个资产**，按触发字段拆分：

| 字段 | 次数 |
|---|---|
| fingerprint_hash | **1,481** |
| cnames | **1,408** |
| status_code | 807 |
| title | 442 |

**根因**：多线 CDN 的同一主机在每轮解析中在几条线之间轮换，CNAME 集合必然变化。实例（`events.detail` 原文）：

```
www.haimian.com
  old: ["www.haimian.com.bytedns3.com", "www.haimian.com.230b2a2545cfa773.w.cdngslb.com"]
  new: ["www.haimian.com.bytedns3.com", "www.haimian.com.c.dsa.cdnbuild.net", "l7-online-self-max-v6.s.dsa.cdnbuild.net"]
```

单主机 3 天内触发 5 次 changed（= 每轮扫描一次）。`fingerprint_hash` 因包含 title/tech 也跟着翻。

**影响**：事件流被噪声淹没，真实新增/变更被埋；`New-SrcHunt.ps1 -IncludeChanged` 拉到的目标里大量是这种无效变更。

**建议**：
1. 对 `cdn IS NOT NULL` 的资产，`cnames` 变化不生成 changed 事件（CDN 线路变化无安全意义）；
2. `fingerprint_hash` 变化不单独成事件（它已由 status/title/tech 覆盖，重复计数）；
3. 或引入"连续 N 轮一致才上报"的去抖。

实测：24h 内 cdn 资产贡献 268(tencent)+213(akamai)+50(bytedance)+33(wangsu)+25(aliyun)+… ≈ 600 条，其余 2,278 条落在 `cdn` 为空的资产上（多为 360.cn/qq.com 这类多线自建 CDN，识别未覆盖）。

## 三、[P1] `alive='dead'` 语义混淆：DNS 失败和 HTTP 不通混在一起

抽样 10 个近 2 天内标记为 `dead` 的资产，实测结果：

| 主机 | 现状 | 判定 |
|---|---|---|
| slink.kwai.com | 可解析（103.167.26.140 / 162.62.83.81） | ❌ **DNS 假阴** |
| dev.ailearning.qq.com | 可解析，但 HTTP 不通 | ✅ dead 合理（HTTP 层） |
| dalaihu.dujia.qunar.com | 可解析，同时被标 wildcard=t | ✅ 泛解析 |
| youshuihe.dujia.qunar.com | 同上 | ✅ 泛解析 |
| en.so.com / oa.corp.qihoo.net / www.d.xiaomi.com / qbimg.nfa.qq.com / mx-jx77-81.meituan.com / uat-aws.jtexpress.com.cn | 均 NXDOMAIN | ✅ dead 合理 |

**问题**：`assets.alive` 只有 alive/dead/unknown 三态，`dead` 同时表示"DNS 不解析"和"HTTP 不通"，用户无法区分"这站没了"还是"只是没开 web"。
**建议**：`dead` 时用 `resolved` 字段 + 新增 `http_failed` 语义区分；或 UI 上把"DNS 死"和"HTTP 死"分开展示。

> 顺带：`dalaihu.dujia.qunar.com` 出现 `resolved=t + wildcard=t + alive=dead` 的组合，状态机里可读性较差，建议核对 wildcard 资产的 alive 语义。

## 四、[P1] passive 扫描零统计、失败静默

**事实**：`scan_tasks` 里 594 条 passive 任务的 `result` **全部为 NULL**（只有 active/dns/http 写 result）。

结合 `passive.go:281` 的逻辑：

```go
if len(errs) == len(srcs) && len(srcs) > 0 {   // 只有「所有源都失败」才报错
    return nil, errors.Join(errs...)
}
```

而 `subfinderEnum` 内部吞掉所有源错误并返回空列表 → **"crt.sh 挂了 + subfinder 也全挂" 的任务会以 `done` + 0 资产收场，无任何痕迹**。

这正是之前 `oceanbase.com` 三轮扫描"啥都没跑出来"的成因；今天 crt.sh 仍间歇 429/502/transport fail，这类静默失败随时会再发生。

**建议**：
1. passive 任务把 `{sources_ok, sources_failed, found}` 写进 `result`；
2. 当所有源都无结果且至少一个源报错时，标记 `degraded=true` + `degraded_reason`（schema 里已有这两个字段，`scanSelect` 已在读）。

## 五、[P2] 历史同步数据的 `first_seen` 污染"今日新增"

**事实**：12,568 条 `history_sync` 资产的 `first_seen` = 我执行同步的时间（11-02/11-03），因为 SQL 用了 `now()` 默认值。

**影响**：`/api/assets?new_since=` 与 `New-SrcHunt.ps1` 的时间窗会把这些**已挖过的历史资产**当成"本轮新增目标"。今天跑 `-Src 腾讯` 得到 1,116 个目标，里面就混着这类历史条目，等于让你重挖。

**建议修复（一行 SQL，等你确认再执行）**：

```sql
-- 把「纯历史同步、从未被真实扫描碰过」的资产 first_seen 回填为历史时间
UPDATE assets
SET first_seen = '2026-01-01 00:00:00+00'
WHERE sources = ARRAY['history_sync']        -- 仅历史同步、无其它来源
  AND resolved_at IS NULL;                    -- 从未被 dns 扫描过
```

## 六、[P2] 单根域超大任务长时间占用 worker

`qq.com` 的 http 任务（id 8928）已连续跑 **60+ 分钟**（27,485 个资产 × 2 scheme @ HTTP_RPS=10）。虽然 asynq 有租约与重试，但：

- 占用 1/10 的 worker 并发槽 1 小时；
- 期间该根域任何新资产都要等下一轮；
- 一旦中途容器重启，整轮白跑（这也是我们历史上反复出现"僵尸 running"的根源之一）。

**建议**：http/dns handler 内部按 `hosts` 分片（如每 2,000 个一批）独立入队，失败/重启只重跑一片。

## 八、[P2] 容量评估：根域从 125 涨到 306

| | 之前 | 现在 | 预计全量轮转后 |
|---|---|---|---|
| 根域 | 125 | 306 | 306 |
| passive 任务/天（6h×4） | 500 | 1,224 | 1,224 |
| 连带 dns+http 任务/天 | ~1,500 | ~3,672 | ~3,672 |
| 实测日吞吐（11-03） | — | 1,966 | 需要 ≈2x |

现在 12h 内跑了 291 passive + 484 dns + 577 http，尚能跟上；但 306 个根域全量轮转后每天约 3,700 个任务，**单 backend 会长期处于高负载**。

**建议**（任选）：
- 把 `SCHEDULE_PASSIVE` 从 `6h` 调到 `12h`；
- 或对大域（qq.com / qunar.com / woa.com 等 >5,000 资产的）单独降频；
- 或加第二个 backend 副本（注意 asynq 并发与 DNS_QPS 是单实例配置，多副本会翻倍实际速率）。
