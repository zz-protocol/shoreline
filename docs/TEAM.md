# 岸线开发团队与流程

这份文档规定「谁拍板、谁实现、谁验收、怎么交接」。规格与任务的唯一出处仍是根目录 `SPEC.md` 与 `TASKS.md`；运行与接口事实看 `docs/REFERENCE.md`。三者冲突时以 `SPEC.md` 为准。

## 1. 角色

| 角色 | 职责 | 禁止 |
|---|---|---|
| 开发-产品架构 | 唯一对用户说话。把需求写进 `SPEC.md`（按轮追加），拆成带编号、验收标准、状态的 `TASKS.md` 行；确认需求后派工；回答工程与交付的规格疑问；验收通过后自己核对代码与测试，再向用户汇报。 | 不写功能代码，不部署，不替用户做产品决定。 |
| 开发-工程 | 按 `TASKS.md` 实现后端、前端、联调、测试，同步 OpenAPI/MCP/`docs/REFERENCE.md`；小提交、带任务号；把任务改为「待验收」后交交付。 | 不直接对用户承诺完成或上线，不改 SPEC 口径，不部署，不对真实厂商扫描，不自己写「完成」。 |
| 开发-交付 | 拿 SPEC 的验收标准从头重跑，不信工程自测；按 `scripts/accept.ps1` 与 `docs/REFERENCE.md` 核对；通过改「完成」并写证据，不通过改「打回」并写可复现原因。 | 不直接对用户说话，不改规格，不替工程补功能。 |

用户只面对架构。工程与交付的消息先到架构，由架构汇总。

### 本机如何落地三角色

- **架构**：当前 grok cli 主会话。
- **工程**：`spawn_subagent` 起实现子代理，必要时 `isolation="worktree"` 隔离；子代理只拿到任务段落、红线、验证命令，不拿验收判断权。
- **交付**：另起一个独立子代理，只读代码与测试，按 `scripts/accept.ps1` 跑；不与工程共用上下文。
- **Orca**：需要与主会话并行、或需要真浏览器验收时用 Orca worktree / 终端；一个任务一个 worktree，合并由架构做。

一个人兼做时仍按「先写规格 → 再实现 → 另起一次独立验收」三步走，不允许实现者自己宣布完成。

## 2. 状态机

只允许五个值：**待做 / 进行中 / 待验收 / 完成 / 打回**。

| 动作 | 允许的人 |
|---|---|
| 待做 → 进行中 | 工程 |
| 进行中 → 待验收 | 工程（附提交号） |
| 待验收 → 完成 / 打回 | 交付（附证据或打回原因） |
| 打回 → 进行中 | 工程 |
| 改任务范围、验收标准、依赖顺序 | 架构（先改 SPEC，再改 TASKS） |

## 3. 标准流水线

1. 用户提需求或方向；架构拿不准只问一个具体问题。
2. 架构写 `SPEC.md` 新一轮或新段落：背景、定义、红线、非目标、每个任务的可测验收标准、依赖顺序。
3. 架构同步写 `TASKS.md`：编号接着编，状态「待做」。
4. 提交并推 `master`，再派工。派工必须写清：读哪段 SPEC/TASKS、红线、依赖、验证命令、做完改「待验收」、疑问找架构。
5. 工程实现：小提交带任务号；实现提交与「改为待验收」文档提交分开；REST、`backend/openapi.yaml`、MCP、前端、`docs/REFERENCE.md` 一起改；测试只用假服务与 mock。
6. 交付独立验收：`scripts/accept.ps1 -Task T5x`，必要时 `scripts/check.ps1 -Scope All -Count 2`；关键路径用真后端 + 生产构建 + 无头浏览器；对打回点做回归与小变异。
7. 架构核对代码与测试，重点看 IP 脱敏、门控顺序、默认关闭，再向用户汇报。
8. 部署只在用户明确授权后进行，按 `docs/DEPLOY.md` 先备份。

## 4. 派工模板

```text
角色：开发-工程
任务：T5x（读 SPEC.md 第 N 轮「T5x」段与 TASKS.md 对应行）
依赖：T5x-1 已验收 / 无
红线：不部署、不对真实厂商扫描、不写生产地址、IP 不存不显、不改 SPEC 口径
验证：scripts/check.ps1 -Scope All；scripts/accept.ps1 -Task T5x
交付：实现提交 + 测试 + 文档同步；TASKS.md 状态改「待验收」并写提交号
疑问：回给架构，不要自行改需求
```

## 5. 验收模板

```text
角色：开发-交付
任务：T5x
输入：SPEC 验收条目、TASKS 行、工程提交号、scripts/accept.ps1
做法：按验收条目逐条跑；测试用可破坏库；关键路径真构建 + 无头浏览器；打回点做变异回归
输出：通过 → TASKS 状态「完成」+ 证据（提交号、命令、耗时、变异结果、无真实网络）
      不通过 → 状态「打回」+ 可复现步骤 + 期望 vs 实际
禁止：替工程改代码、改验收标准、口头通过
```

## 6. 文档格式

- `SPEC.md`：按轮追加，不删旧轮。每轮含背景、定义（如「冷门」）、已确认口径、非目标、任务小节（数据/行为/接口/验收）、依赖。
- `TASKS.md`：四列表格（编号、任务、验收标准、状态）。完成或打回的证据写进状态格，不另开日记。
- `docs/REFERENCE.md`：运行与接口事实（环境变量默认值、门控顺序、扫描类型）。实现改了配置或口径要同步；新口径先出现在 SPEC。
- 对外文档禁止写生产公网地址或 IP。
- 提交信息：「T51 返工: …」「docs/TASKS: 同步 …；T51 待验收」「TASKS: T51 打回（提交号）」。直接在 `master` 推。

## 7. 产品红线（已拍板）

- 定位：从 Web 资产发现扩成全服务冷门组件发现，白盒审计是独立下游。
- 冷门：总体用者少、这家 SRC 用得多、公开披露少；CVE 只做辅助情报。
- 不重写：Go + PostgreSQL + Valkey/Asynq + React。
- 只扫确认非 CDN 的源站；`cdn_fronted` 为空（未判定）也跳过。
- IP 不存不显：只在扫描内存里用；banner 中脱敏为 `[ip]`。
- 非 Web 探测默认关：`SERVICE_SCAN_ENABLED=false`；授权范围按域登记，空范围=未授权；`SCHEDULE_SERVICE` 默认禁用。
- 探测只发无认证、不读写业务数据的只读识别报文，且必须由 YAML 声明。
- 拨号只拨判定时解析到的 IP；拒回环、私网、链路本地、未指定、云元数据。
- 未识别 banner 聚类为 `unidentified-service-<hex>`，`confirmed=false`，可确认或忽略。
- 开发验收红线：不部署、不对真实厂商扫描、不写生产地址、不删除已识别组件数据。

## 8. 本机执行环境

- 后端测试：宿主机没有 Go，用 `golang:1.26-alpine` 容器跑，`scripts/check.ps1` 已封装。
- 格式检查：Windows checkout 为 CRLF，`check.ps1` 默认跳过 `gofmt`；CI 或 Linux 环境加 `-Fmt`。
- 测试库：`shoreline-postgres-1` 上的 `sam_test`，脚本会自动创建；不要指向有生产数据的库。
- 前端：`npm ci` + `npm test -- --run` + `npm run build`，脚本封装。
- 服务：`docker compose up -d`；Web `127.0.0.1:5173`，API `127.0.0.1:8080`。
- 当前代码注意：本机 HEAD 为 `778de62`，前一份交接提到的 `c3130ff`、`5844c22` 与未提交 T53 实现不在本机。T53 需要重做或从旧环境取回，开工前先确认。

## 9. 交接与并行

- 一个任务一个 worktree 或一个子代理；同一时间一个实现 + 一个验收。
- 迁移文件编号连续（当前到 `030`），涉及迁移的任务串行。
- 两个任务都要改 `TASKS.md`/`REFERENCE.md` 时，由架构合并文档提交。
- 子代理交付必须包含：改了什么、怎么验证、遗留缺口、迭代建议。
